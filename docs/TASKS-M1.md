## 결정 (2026-09-24)

PK는 `ID int64`(D-74), NULL은 포인터(D-75), 테이블 `앱_모델`·컬럼 snake_case(D-76), v0 필드 타입(D-77, 아래 표),
`fk=`는 같은 앱만(D-78), M1의 `models_gen.go`는 D-18 주석만(D-79). 태그 안의 필드 이름은 Go 필드 이름(D-80).

필드 타입 (v0, D-77)

| Go | SQLite | PostgreSQL | 비고 |
|---|---|---|---|
| `int64` | `INTEGER` | `BIGINT` | `ID int64`는 PK: SQLite `INTEGER PRIMARY KEY`, PG `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `int32` | `INTEGER` | `INTEGER` | |
| `bool` | `INTEGER` | `BOOLEAN` | SQLite는 `CHECK (x IN (0, 1))` |
| `float64` | `REAL` | `DOUBLE PRECISION` | |
| `string` + `max=N` | `TEXT` | `VARCHAR(N)` | SQLite는 `CHECK (length(x) <= N)` |
| `string` | `TEXT` | `TEXT` | |
| `time.Time` | `TEXT` | `TIMESTAMPTZ` | SQLite는 RFC 3339 문자열 |
| `[]byte` | `BLOB` | `BYTEA` | |
| 위의 포인터 | 같음, `NULL` 허용 | 같음, `NULL` 허용 | 포인터가 아니면 `NOT NULL` |

그 밖의 타입(`int`, `uint*`, `float32`, 사용자 타입 …)은 D-18에 따라 이유와 함께 주석으로 남기고 스키마에서 뺀다.

## 1. 런타임 `maago.Model`

- 루트 패키지에 첫 공개 타입: 임베드용 빈 struct `maago.Model`. 메서드 없음
- 생성기는 이 타입을 import 경로와 이름으로 알아본다(`go/ast`, 타입 검사 없음, ARCHITECTURE A-3)

→ 확인: `go vet ./... && go test ./...`가 통과한다(테스트 파일의 예제 모델이 `maago.Model`을 태그와 함께 임베드한다). 루트 `go.mod`에 `require`가 없다

**계획**
- 새 파일: 루트 `model.go`(`type Model struct{}`와 문서 주석), `model_test.go`(package `maago_test`, `ExampleModel`)
- 문서 주석에 쓰임새 예: 임베드한 `maago.Model`의 태그가 모델 옵션(D-13), PK는 `ID int64`(D-74), 포인터는 NULL(D-75)
- `ExampleModel`은 출력 없는 예제라 실행되지 않고 컴파일만 된다. 외부 패키지(`maago_test`)에서 임베드가 되는지가 이 작업의 확인이다
- 첫 필드여야 하는지, 포인터 임베드(`*maago.Model`)를 받을지, import 별칭(`m "…/maago"`, `.`)을 어디까지 알아볼지는 두지 않는다. 생성기가 알아보는 일이라 4번이 정한다
- 구현 리뷰: codex(문서 주석 예제에 import가 없음 → 받지 않음: Go 문서 주석의 조각 예제 관례), fable(D-10 인용이 맞지 않음 → 번호를 뺌). 둘 다 그 밖의 문제 없음
- 리뷰: codex(예제에 태그 있는 임베드, 포인터·별칭은 4번으로) 반영. "D-10의 근거가 틀렸다"는 받지 않음: D-10은 키 없는 태그(`"max=200"`)를 말하고, 그것은 `go vet`의 structtag가 실제로 경고한다. fable(확인 명령을 `go vet`·`go test`로 명시) 반영
- 하지 않는 것: 메서드, 필드, `doc.go`의 문구 변경

## 2. 프로젝트 읽기 (`internal/project`)

- 작업 디렉터리에서 위로 `go.mod`를 찾아 프로젝트 루트를 안다
- `./...` 훑기(M0 8번의 `Owned`와 같은 규칙)를 여기로 옮기고 `pipeline`이 이것을 쓴다
- 앱(= `maago.Model`을 임베드한 struct가 있는 패키지, ARCHITECTURE §5) 판정은 소스를 해석해야 하므로 4번이 한다
- `pipeline`이 `project`를 import하므로 `project`는 `pipeline`의 타입(`Step`, `Run`)을 쓸 수 없다. 단계 조립은 둘을 모두 import하는 곳(9번)에서

→ 확인: `go.mod`가 없으면 찾아본 디렉터리와 고치는 법이 있는 진단. 하위 모듈·`testdata`·`vendor` 안의 파일은 목록에 없다. `pipeline`의 테스트가 그대로 통과한다

**계획**
- 새 파일: `internal/project/project.go`, `project_test.go`. 바꿀 파일: `internal/pipeline/pipeline.go`(`Owned`가 `project.GoFiles`를 쓴다)
- `Root(dir string) (string, []diag.Diagnostic)`: `dir`을 절대 경로로 만들고 symlink를 푼 뒤, 위로 `go.mod`가 있는 디렉터리를 찾는다. 부모가 자기 자신이면(파일 시스템·볼륨 루트) 멈춘다. 없으면 위치 없는 진단, 메시지에 찾기 시작한 디렉터리, fix `run maago inside a Go module; create one with go mod init`. `go.mod`의 `Stat` 오류가 "없음"이 아니면 그 오류로 진단
- `GoFiles(root string) ([]string, []diag.Diagnostic)`: `root`의 symlink를 풀고(M0 8번의 `EvalSymlinks`를 여기로. `pipeline`을 symlink 루트로 직접 부르는 테스트가 있다), `./...` 규칙(M0 8번 그대로)으로 `.go` 파일(테스트 포함)의, 루트 기준 슬래시 경로를 정렬해 돌려준다. 표시가 있는 `_gen_test.go`도 생성물이므로(D-67) 빼지 않는다. 모델을 찾을 때 테스트 파일을 건너뛰는 일은 4번이 한다. 훑다 난 오류는 진단으로 모으고 계속 훑는다. 하위 디렉터리의 `go.mod`를 읽을 수 없으면 진단하고 들어가지 않는다(다른 모듈일 수 있고, gen은 파일을 지운다). `pipeline.Owned`는 이 목록을 읽어 표시만 본다. 훑기 규칙은 이제 여기 한 곳에만 있다
- 모듈 경로(`module` 줄)는 읽지 않는다. M1에서 쓰는 곳이 없다(import 경로는 `maago` 자신의 것만 본다). 쓰는 곳이 생기면 더한다
- "앱 = `maago.Model`을 임베드한 struct가 있는 패키지"의 판정은 Go 소스를 해석해야 하므로 4번(`model`)이 한다. `project`는 파일 목록까지
- `project`는 `pipeline`을 import하지 않는다(순환). 단계 조립은 9번
- 하지 않는 것: `go.work`, 모듈 경로, 빌드 태그 해석
- 리뷰: codex(위로 찾기의 멈춤 조건, "없음" 외 `Stat` 오류, `GoFiles`도 symlink를 풂, 루트 기준 경로, 훑기 오류, symlink 디렉터리 테스트), fable(같은 symlink 회귀, 작업 본문을 계획에 맞춤, 진단에 디렉터리, `_test.go` 결정, macOS `/private/var`) 모두 반영. 구현 리뷰: codex(하위 `go.mod`의 읽기 오류를 모듈 아님으로 봄 → 진단하고 들어가지 않음, 상대 경로·읽기 오류 테스트), fable(`_test.go`를 빼면 표시 있는 `_gen_test.go`를 gen·check가 못 봄(D-67) → 다시 담음, 정렬되지 않음 → `slices.Sort`, 오류 경로 돌연변이 8개 → 테스트 추가, 같은 한 줄 함수가 두 곳 → `diag.OneLine`) 모두 반영

→ 확인 (`go test -count=1 ./internal/project ./internal/pipeline`)
1. 하위 디렉터리에서 `Root`가 위의 `go.mod` 디렉터리를 찾는다. symlink로 들어가도 같은 실제 경로(`EvalSymlinks`한 임시 디렉터리와 비교)
2. `go.mod`가 없는 곳(임시 디렉터리)에서는 진단 하나, 메시지에 그 디렉터리, 고치는 법에 `go mod init`
3. `GoFiles`가 M0 8번의 건너뛰기 규칙을 모두 지키고(`testdata`, `vendor`, `.`·`_`, 하위 모듈, symlink 파일과 symlink 디렉터리), `_test.go`도 담으며, 경로는 정렬된 슬래시 경로(`blog.go`가 `blog/…`보다 앞)
5. 오류 경로: `Root(".")`(작업 디렉터리가 하위), 없는 디렉터리, 읽을 수 없는 하위 디렉터리(진단 하나, 나머지는 계속, 이름의 줄바꿈은 `\n`으로)
4. `pipeline`의 테스트가 고치지 않고 그대로 통과한다

## 3. 태그 문법 (`internal/model`)

- `maago:"…"` 값 → 키·값 목록. `,` 구분, `'…'` 문자열(`''`는 `'`), `(a,b)` 묶음, `a/b/c` 선택지, 같은 키 반복(D-13, 기호 표)
- 문법 오류의 위치는 태그 안의 칸까지(`파일:줄:칸`)
- `reflect.StructTag`는 쓸 수 없다(생성기도 reflect 게이트 대상, ARCHITECTURE §7). 바깥 `key:"value"`도 직접 해석한다. 칸이 정확한 것은 백쿼트 태그뿐이므로, 큰따옴표 태그를 어떻게 다룰지 계획에서 정한다

→ 확인: 기호 표의 모든 형태와 잘못된 형태(닫히지 않은 `'`, 빈 키, 짝 없는 괄호)가 골든 파일과 같다

**계획**
- 새 파일: `internal/model/tag.go`, `tag_test.go`, `testdata/tag.golden`
- `ParseTag(fset, lit *ast.BasicLit) ([]Option, []diag.Diagnostic)`. 키 이름이 허용 목록에 있는지, 값의 뜻은 4번이 본다. 여기는 문법만
- 바깥층(Go 태그)은 `reflect.StructTag.Lookup`의 규칙을 그대로 따라 직접 해석한다(reflect 게이트): 쌍 사이 구분은 ASCII 공백만, 키는 공백·`:`·`"`·DEL이 아닌 바이트, 값은 `"…"`. 어긋나면 진단. `Lookup`과 다른 곳은 둘: `maago` 값은 `strconv.Unquote`하지 않고 바이트 그대로 쓴다(그래야 값의 i번째 바이트가 파일의 한 칸), `maago:`가 두 번이면 첫 것을 쓰지 않고 진단. `maago:` 키가 없으면 옵션도 진단도 없다
  - 태그는 한 줄의 백쿼트 문자열로만 받는다. 큰따옴표 태그는 이스케이프 때문에, 여러 줄 태그는 백쿼트 문자열이 `\r`을 버려서 칸을 정확히 짚을 수 없다 → 진단(fix: 백쿼트로, 한 줄로)
  - `maago:"…"` 값 안의 백슬래시도 진단. 문자열은 `'…'`로 쓰므로 필요 없다. 그 결과 값에 `"`는 쓸 수 없다(label·help 포함). 한계로 TODO에 적는다
  - 칸은 바이트 기준(Go의 `token.Position`과 같다). 한글 뒤의 칸도 바이트로 센다
- 안층(maago 값) 문법:
  ```
  options = option { "," option }
  option  = key [ "=" value ]
  key     = "a"…"z" { "a"…"z" }
  value   = string | group | bare { "/" bare }
  string  = "'" { 따옴표가 아닌 문자 | "''" } "'"
  group   = "(" bare { "," bare } ")"
  bare    = 1자 이상, `,()'/=`·공백·`"`·`\`가 아닌 문자
  ```
  - 문자열은 SQL과 같다: `''`만 있으면 빈 문자열, `''''`는 작은따옴표 하나. 쉼표가 든 값은 `'a,b'`
  - 선택지(`draft/published`)는 `/`로 이은 bare. `choices=draft`처럼 하나여도 같은 모양이다. 묶음(`(a,b)`)의 항목은 bare
  - 같은 키 반복은 그대로 목록에 둔다(D-13, 겹침 검사는 4번)
  - 문자열 밖의 공백은 진단(fix `remove the space`). 허용하면 "공백이 뜻을 가지는가"를 따로 설명해야 한다(PHILOSOPHY 3)
- 결과 타입: `Option{Key string; KeyPos token.Pos; Kind Kind; Values []string; ValuePos []token.Pos}`. `Kind`는 `NoValue`(키만), `Bare`(`/`로 나뉜 1개 이상), `String`, `Group`. `String`과 `Group`은 D-14와 기호 표가 따로 정한 모양이라 나눈다. 값마다 위치를 둬 4번이 항목을 짚는다
- 오류: 한 태그 안에서는 첫 오류에서 멈춘다(그 뒤는 연쇄). 다른 필드의 태그는 계속 본다(D-61)
- 완료 때 DECISIONS에: 태그는 한 줄 백쿼트, 값 안에 백슬래시·`"`·문자열 밖 공백 없음
- 하지 않는 것: 키 이름·값의 뜻 검사(4번), 공백 허용, 큰따옴표·여러 줄 태그, 값 안의 `"`
- 리뷰: codex(`Lookup` 규칙을 정확히, `\r` 때문에 여러 줄 금지, 칸은 바이트, `''` 경우 명시, 키 문법) 반영. codex의 "`/`가 bare에서 빠지지 않았다"는 잘못 읽은 것(계획에 이미 빠져 있다). fable(세 규칙은 계획의 선택이고 완료 때 DECISIONS에, `"`를 못 씀을 명시, `Lookup`과 다른 두 곳, 골든에 모든 위치, 빠진 경우들, `Kind`에서 선택지를 bare로 합침) 모두 반영. 구현 리뷰: codex("값 안의 `"`" 판단이 뒤쪽 형식 오류에도 걸림 → maago 값에 닫히지 않은 `'`가 있을 때만, 태그 없는 필드의 `nil`은 옵션 없음) 반영, 다른 키 값의 이스케이프 검사는 받지 않음(`Lookup`도 찾는 키만 Unquote한다). fable(`maxLen=1`에 "쉼표로 나누라"는 틀린 fix → 키 토큰을 통째로 읽고 소문자를 요구, 값 뒤의 `=`·`'`에는 `'text'`로 쓰라는 fix, 닫히지 않은 바깥 `"` 경우 추가, D-81) 반영. 골든은 생성 뒤 칸마다 손으로 확인했다

→ 확인 (`go test -count=1 ./internal/model`, 골든은 옵션마다 키·종류·값과 모든 위치를 찍는다)
1. 기호 표의 모든 형태(`,`, `'…'`과 `''`·`''''`·`'a,b'`, `(a,b)`, `a/b/c`, 같은 키 반복, 값 없는 키), `maago:`가 첫 키가 아닌 태그, 한글 뒤의 값, `maago:` 키가 없는 태그(옵션·진단 없음)의 결과가 골든과 같다
2. 잘못된 형태 각각(닫히지 않은 `'`, 빈 키 `,,`, 끝 쉼표, 짝 없는 `(`, 빈 묶음 항목, `=` 뒤 값 없음, 대문자 키, 공백, 백슬래시, 값 안의 `"`, 큰따옴표 태그, 여러 줄 태그, `maago:` 두 번, Go 태그 형식 오류)이 정확한 `파일:줄:칸`과 함께 골든과 같다
3. 한 태그의 오류 둘은 진단 하나(연쇄 차단), 여러 필드의 오류는 모두 나온다

## 4. 모델 읽기와 검사

- `go/parser`로 앱 패키지를 읽어 모델을 찾고, 필드 태그를 닫힌 목록으로 검사한다(D-10, D-17)
- 모르는 키는 가장 가까운 키로 "did you mean"과 허용 목록(편집 거리)
- 모델 태그 `table`·`ordering`·`unique=(a,b)`·`index=(a,b)`, 필드 태그 `max`·`unique`·`index`·`default`·`choices`·`label`·`help`·`fk`(D-12~D-14)
- 값 검사: `max`는 양의 정수이고 `string`에만, `choices`의 기본값은 선택지 안에, `fk` 대상 모델이 같은 앱에 있다(D-78), 묶음의 필드가 있다, PK 규칙(D-74)
- `default` 값이 필드 타입(D-77)으로 해석되는지도 검사한다(M2까지 미루지 않는다)

## 5. 제약 모으기 (`internal/model`)

사람의 결정(2026-09-25): 방언 중립 스키마 계층은 M2로 미룬다. M2에서 DB를 다시 읽어 비교할 때, 읽어 오는 쪽에 맞춰 만든다. 6·7번은 검사된 `model.App`을 바로 읽는다. FK는 `ON DELETE NO ACTION`(D-84), FK 컬럼에는 인덱스를 자동으로 만든다(D-85), 제약 이름은 PG 방식을 DDL에 명시한다(D-86).

- 필드의 `unique`와 모델의 `unique=(a,b)`를 한 목록(`Model.Uniques`)으로, 필드의 `index`와 `index=(a,b)`와 FK 자동 인덱스를 한 목록(`Model.Indexes`)으로 모은다. 항목은 컬럼 이름
- 같은 컬럼 집합의 unique가 두 번(필드 `unique`와 `unique=(Field)`) 또는 index가 두 번 선언되면 진단. FK 자동 인덱스는 같은 컬럼의 unique나 index가 이미 있으면 만들지 않는다(사람이 쓴 것과 겹치는 것은 오류가 아니다)
- 두 필드가 같은 컬럼 이름이 되면(`AuthorID`와 `AuthorId` → `author_id`) 뒤 필드 위치에 진단
- 제약 이름은 방언이 붙인다(`internal/dialect`의 공통 함수: `테이블_컬럼들_key`·`_idx`·`_fkey`). PG의 63바이트 한도는 PG 방언의 검사다(D-31: SQLite 프로젝트에 PG 오류를 내지 않는다)

- unique는 컬럼 집합으로 겹침을 본다(`(a,b)`와 `(b,a)`는 같다). index는 순서가 뜻을 가지므로 다르다
- 리뷰: codex(unique는 집합으로 비교, 이름 충돌 때 FK 자동 인덱스가 둘 생김) 반영. fable(D-85의 "이미 있으면 만들지 않음"을 시험하는 예제가 없음 → FK에 unique·index를 단 필드 추가, unique와 index를 함께 단 컬럼, 남아 있던 스키마 계층 문구) 반영

## 7. PostgreSQL DDL (`internal/dialect/postgres`)

→ 확인: 예제 모델 셋의 DDL이 골든과 같다(M1 완료 조건 2)

**계획**
- 새 파일: `internal/dialect/postgres/postgres.go`, 테스트, `testdata/example.sql`(골든), `testdata/smoke.sh`
- `postgres.DDL(fset, apps) (string, []diag)`. 먼저 `dialect.CheckNames(…, 63)`, 그리고 테이블·컬럼 이름이 63바이트를 넘으면 진단(PG는 조용히 자른다)
- 문장 순서: 모든 `CREATE TABLE` → 모든 FK(`ALTER TABLE … ADD CONSTRAINT "t_c_fkey" FOREIGN KEY … ON DELETE NO ACTION`) → 모든 `CREATE INDEX`. PG는 아직 없는 테이블을 참조할 수 없으므로 FK를 테이블 뒤로 뺀다. 자기 참조와 앱 안의 순환도 같은 방법으로 풀린다
- 컬럼(D-77): `int64` `BIGINT`, `int32` `INTEGER`, `bool` `BOOLEAN`, `float64` `DOUBLE PRECISION`, `string`+`max` `VARCHAR(N)`(CHECK 없음, 문자 수), `string` `TEXT`, `time.Time` `TIMESTAMPTZ`, `[]byte` `BYTEA`. `"id" BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`(PK 이름은 PG가 붙이는 `t_pkey`). 포인터가 아니면 `NOT NULL`. `choices`는 `CHECK ("c" IN (…))`
- 기본값: `bool`은 `true`/`false`, 수는 `dialect.Number`, 문자열은 `dialect.String`
- unique는 테이블 제약 `CONSTRAINT "t_c_key" UNIQUE (…)`(PG에서는 제약이 이름을 지킨다. SQLite와 다르게 쓰는 이유는 D-87). index는 `CREATE INDEX "t_c_idx"`
- 두 방언에 같은 `tables` 표(모델 이름 → 테이블)가 생기면 `dialect`로 올린다
- 하지 않는 것: 스키마(`search_path`) 지정, `IF NOT EXISTS`, 실제 적용 Go 테스트(M2)

→ 확인
1. `go test -count=1 ./internal/dialect/...`: 예제 셋의 PG DDL이 골든과 같다(M1 완료 조건 2의 PG 쪽)

D-35의 "개발 DB의 임시 스키마"와 달리 임시 클러스터를 쓰는 것은 사용자의 서버를 건드리지 않기 위해서다). codex(테이블·컬럼·`_pkey` 이름 길이, 테이블과 인덱스가 한 이름 공간, `mktemp`와 trap으로 정리, TCP 끔, `-0`은 `0`으로 정규화(두 방언), IDENTITY BY DEFAULT의 명시 id는 시퀀스를 올리지 않음을 주석으로) 반영. fable(범위 변경은 사람에게, `initdb`는 PATH에 없음 → `pg_ctl`의 링크로 bin을 찾고 없으면 실패, NULL id 경우는 PG에서 `id`를 빼는 것으로, 경우마다 `BEGIN … ROLLBACK`으로 격리, 이름 길이는 제약 없는 모델로 시험, 단계 안의 순서는 모델 순서) 반영. `tables` 표는 `dialect.Tables`로 올렸다

## 9. `gen`·`check` 연결

- 단계 조립: 읽기(2) → 해석(`go/parser`와 태그 문법, 3) → 검사(4·5) → 생성(8). 해석이 실패한 파일을 검사하면 연쇄 오류가 나므로 해석은 따로 단계다(ARCHITECTURE §3, D-61). 조립은 `pipeline`과 `project`·`model`을 모두 import하는 곳에서 하고, 그 위치와 `Run`의 필드는 이 작업의 계획에서 정한다
- CLI의 stub을 걷어내고 `pipeline.Gen`·`Check`를 부른다. `gen`은 지운 파일을 출력한다

→ 확인: 예제 프로젝트에서 `maago gen` → `maago check` 통과. `maxlen` 예제에서 `maago gen`이 1로 끝나고 아무것도 쓰지 않는다. 생성물을 손으로 고치면 `maago check`가 1

**계획**
- 새 패키지 `internal/build`: 단계 조립. `model`→`pipeline`→`project`의 import 방향 때문에 조립은 이들을 모두 import하는 곳이어야 하고, ARCHITECTURE §2와 D-68은 `cmd/maago`를 디스패치만 하는 곳으로 둔다. 루트 모듈의 `go test ./...`가 이 패키지를 시험한다. §2의 트리에 한 줄
  - `Gen(dir string) (removed []string, ds []diag.Diagnostic)`, `Check(dir string) []diag.Diagnostic`. 둘 다 `project.Root(dir)`로 루트를 찾고, 같은 단계 목록을 부를 때마다 새로 만든다
  - 단계: 해석(`project.GoFiles` → `model.Read`) → 검사(`model.Check`, 그리고 `dialect.CheckNames(…, 0)`: 이름 충돌은 두 방언 모두의 오류라 방언을 모르는 M1에서도 잡는다. PG의 63바이트는 방언을 알게 되는 M2에서) → 생성(`model.Files`를 `Run.Files`에 넣음)
  - 단계 사이의 데이터(`fset`, 파일 목록, 패키지, 앱)는 단계 목록을 만드는 함수 안의 변수로 닫아 넘긴다. `pipeline.Run`에 필드를 더하지 않는다(M0 7번에서 미룬 결정의 답)
  - `Gen`은 `pipeline.Gen`, `Check`는 `pipeline.Generate` 후 오류가 없으면 `pipeline.Check(root, files)`
- CLI: stub을 걷어내고 `build.Gen(".")`·`build.Check(".")`. 진단은 `diag.Write`로 stderr, 있으면 1. `gen`은 지운 파일마다 `removed 경로`를 stdout에. 루트 패키지 blank import를 지운다(`build`가 루트 모듈을 쓰므로 `require`가 남는다)
- 진단의 경로는 프로젝트 루트 기준이다(하위 디렉터리에서 돌려도 `blog/models.go:…`). ARCHITECTURE §4에 적는다
- `cmd/maago/main_test.go`의 "not implemented" 경우들을 실제 동작으로 바꾼다
- 하지 않는 것: `.env`와 DDL 파일 쓰기(M2), 진행 출력
