# 마일스톤

[DECISIONS.md](DECISIONS.md)의 단계 열을 만드는 순서로 풀었다. 번호는 순서이자 의존 관계다.
앞 마일스톤이 뒤 마일스톤의 도구가 된다. 괄호 속 번호는 해당 결정이다.

**v0 목표**: 모델 정의 → `makemigrations` → `migrate` → admin CRUD + 로그인까지 5분 (D-69).
v0의 DB는 SQLite와 PostgreSQL이다 (D-30).

---

## v0

### M0. 뼈대

모든 검증이 거쳐 갈 길을 먼저 깐다. 이후 마일스톤은 여기에 검사를 더하기만 한다.

- `go.mod` (`github.com/maago-web/maago`), 단일 바이너리 `maago`와 `flag` 디스패치 (D-03, D-68)
- `maago gen` / `maago check`의 틀: 오류가 있으면 아무 파일도 쓰지 않음, 독립 오류 전부 출력,
  `파일:줄:칸: 메시지` + 고치는 법 (D-60~D-63)
- reflect 금지 게이트와 CI (D-66)

완료 조건
- [x] `reflect`를 import한 임시 파일을 넣으면 CI가 실패한다
- [x] 가짜 오류 두 개를 내는 검사기를 붙이면 두 오류가 한 번에 나오고, 생성물은 하나도 바뀌지 않는다
      (테스트로 확인. CLI 연결은 M1, [TASKS-M0.md](TASKS-M0.md) 끝)

### M1. 모델

- struct + `maago:"…"` 태그를 `go/ast`로 읽는다. 닫힌 목록, 모르는 키는 “did you mean” (D-10, D-17)
- v0 태그 부분집합: 기본 필드 타입, `max`·`unique`·`index`·`default`·`choices`·`label`·`help`,
  `fk=모델`, 모델 태그의 `table`·`ordering`·`unique=(a,b)`·`index=(a,b)` (D-12~D-14)
- 지원하지 않는 필드는 이유와 함께 생성 파일에 주석 (D-18)
- 모델 → 목표 스키마(방언별 DDL)

완료 조건
- [x] `maxlen=200`은 `file:line:col`과 `did you mean "max"`로 실패한다
- [x] 예제 모델 셋(FK, 복합 unique 포함)의 DDL이 SQLite와 PG 골든 파일과 같다 (D-67)
      ([TASKS-M1.md](TASKS-M1.md) 끝)

### M2. 연습용 DB와 마이그레이션

SQL 검증(M3)이 스키마를 필요로 하므로 마이그레이션이 먼저다. 작업 목록은 [TASKS-M2.md](TASKS-M2.md)(진행 중).

- 연습용 DB: SQLite는 메모리, PG는 개발 DB의 임시 스키마. 연결 실패는 켜는 법과 함께 실패 (D-35, D-64)
- 스키마 읽기 → 모델과 비교 → DDL 초안. 외부 라이브러리 없이 (D-33, D-34)
- `makemigrations` / `showmigrations` / `migrate`, 번호 붙은 SQL 파일 (D-32, D-38)
- 이름 변경은 ⚠ 초안 + `--rename`, `DROP`은 `-- maago: allow-drop` 없으면 실패 (D-36, D-37)
- SQLite 테이블 재생성

완료 조건
- [ ] 빈 프로젝트에서 모델 추가 → 필드 추가 → 필드 이름 변경 → 필드 삭제를 차례로 했을 때,
      모든 마이그레이션을 적용한 결과가 모델과 같다 (SQLite, PG 모두)
- [ ] 초안을 손으로 고쳐 모델과 달라지게 만들면 `check`가 실패한다
- [ ] `allow-drop` 없는 `DROP`은 `check`가 실패한다

### M3. SQL 매퍼

- 파일 머리(이름·결과·파라미터), `:이름` 바인딩과 슬라이스 펼치기 (SQL 규칙 1·2)
- `{조건}` 줄, `WHERE { }`·`SET { }` 정리 → Go 코드로 번역 (규칙 3·4, D-22)
- 커버 조합을 연습용 DB에 prepare, 결과 타입 검사와 새 타입 생성 (규칙 5, D-23)
- PK 기준 기본 CRUD 생성 (D-21)
- 할일: 런타임이 DB를 여는 법(D-08은 CLI 전용이고 루트 모듈에는 드라이버가 없다, D-90)과 연결 풀 설정
  (최대 연결 수, 유휴 연결, 연결 수명 max age)의 이름과 기본값. 생성된 매퍼가 DB를 받는 자리라 여기서 정한다

완료 조건
- [ ] DECISIONS의 `SearchOrders` 예제가 생성되고, 조합별로 기대한 SQL이 나온다(골든)
- [ ] 빈 WHERE의 DELETE, 라벨이 보장하지 않는 파라미터, 컬럼이 빠진 모델 결과 타입이 각각 생성 오류다
- [ ] 생성 코드에 `text/template`도 `reflect`도 없다

### M4. HTTP

- 라우트 표 → `ServeMux` 등록과 URL 함수 (D-40)
- 타입 있는 뷰 시그니처와 생성된 어댑터, 표준 핸들러 탈출구 (D-41)
- html/template + 생성 시점 검사: 필드, `{{url}}` 이름·인자 (D-42)
- 태그에서 생성된 폼, (값, 있음, 오류) 구분 (D-43)
- API 라우트와 RFC 9457 오류, `{{block}}` 부분 응답, CSRF (D-44, D-45, D-47)
- **선행 결정 필요**: 서비스 테스트 방법(DECISIONS U-07)

할일 (구체적인 방법은 그 마일스톤의 계획에서 정하고 DECISIONS에 적는다. M5·M6·M7도 같다)
- 폼: 모델에서 만드는 폼과 모델 없는 폼, 필드 검증과 폼 전체 검증, 사용자 검증 함수(D-15: Go 메서드),
  템플릿에서 폼과 오류를 그리는 법 (D-43을 넓힌다. 파일 필드는 M7)
- 현재 사용자와 인증의 **인터페이스**: 뷰가 로그인 여부와 사용자 정보를 얻는 법, 로그인해야만 들어갈 수 있는
  뷰(와 API 라우트)를 선언하는 법(라우트 표·시그니처·미들웨어 중 어디에), 인증 실패의 응답(HTML은 로그인
  화면으로, API는 RFC 9457 401). 세션과 토큰은 M5가 이 인터페이스를 채운다
- CORS: Django(`django-cors-headers`)·FastAPI(`CORSMiddleware`)처럼 허용 출처·메서드·헤더·자격 증명을
  설정으로. D-47의 `http.CrossOriginProtection` 신뢰 출처와 **한 설정**이어야 한다(아니면 허용한 출처의
  POST가 403이 된다)
- 타임존: 저장은 M1에서 정해졌다(PG `TIMESTAMPTZ`, SQLite RFC 3339 글). 남은 것은 기본 표시 타임존과
  템플릿·폼에서의 변환
- 최종 사용자에게 보이는 문구(폼 검증 메시지, 인증·admin 화면)의 언어와 바꾸는 법. 생성 진단은 영어로
  고정(D-06), 필드 라벨은 이미 `label=`(D-14). i18n은 범위 밖(D-72)

완료 조건
- [ ] 템플릿의 `{{.Post.Titel}}`과 없는 URL 이름이 생성 오류다
- [ ] 잘못된 path 값과 `sql.ErrNoRows`는 404, 허용 출처가 아닌 교차 출처 POST는 403이고 허용 출처는 통과한다
- [ ] 로그인 필수로 선언한 뷰에 로그인하지 않고 들어가면 HTML은 로그인 화면으로, API는 401(RFC 9457)
- [ ] 빈 숫자 칸, 범위 밖 숫자, 해석 실패가 폼에서 서로 다른 결과를 낸다

### M5. 인증 (계정 · 이메일)

- 가입·로그인·로그아웃·세션·비밀번호 변경/재설정, 이메일 인증 (D-50)
- User는 contrib 앱, 코어는 인터페이스만 (D-51)
- **선행 결정 필요**: contrib 앱의 모델이 사용자 프로젝트의 스키마·마이그레이션에 들어오는 방식
  (DECISIONS U-06, 지금은 “나중에”로 미뤄져 있다. M5 전에 정해야 한다)
- **선행 결정 필요**: 다른 앱의 모델을 `fk=`로 가리키는 법(D-78이 M5로 미뤘다. `fk=auth.User`에 필요하다)

할일
- User 모델: contrib의 기본 User, 인증(로그인·세션·admin)과의 연결, 커스텀 User(Django의 `AUTH_USER_MODEL`처럼).
  필드를 더하는 법과 통째로 바꾸는 법 중 **하나만**(PHILOSOPHY 3). reflect 없이 생성 코드로 되려면 U-06과 함께
  정해진다. `maago createsuperuser`
- 권한: staff·superuser 구분, 모델별 보기·추가·수정·삭제 권한과 그룹. admin(M6)이 쓴다
- 비밀번호 해싱: 알고리즘과 매개변수, 알고리즘을 바꿀 때 기존 해시를 로그인 때 다시 해싱. 런타임은 stdlib만(D-09)이라
  bcrypt·argon2(`golang.org/x/crypto`)를 쓰려면 D-09를 고쳐야 한다. stdlib의 `crypto/pbkdf2`(Django 기본과 같은
  PBKDF2-SHA256)와 함께 따진다
- 세션: 저장 방식(DB 테이블, 서명된 쿠키 등), 만료, 로그인 때 세션 다시 발급(세션 고정 방지), 서명 키의 보관과 교체,
  쿠키 `Secure`·`HttpOnly`·`SameSite`
- 로그인·비밀번호 재설정의 시도 횟수 제한
- 비밀번호 검증기: 길이, 흔한 비밀번호, 사용자 정보와 비슷한 비밀번호. 규칙은 Go 함수 목록으로 고르고 더한다(D-15,
  Django식 점 경로 문자열은 쓰지 않는다)
- 이메일: 보내는 방식(SMTP, 개발용 콘솔, 테스트용 메모리), 보내는 사람 설정, 메일 템플릿, 인증·재설정 토큰의 만료와
  한 번만 쓰기
- API 인증: 토큰 방식(JWT 등)을 M4의 인증 인터페이스에. M5 안에서 마지막 순서(D-69에는 필요 없다)

완료 조건
- [ ] 가입 → 인증 메일 링크 → 로그인 → 비밀번호 재설정이 통합 테스트로 돈다
- [ ] 인증 테이블이 사용자 프로젝트의 `makemigrations` 결과에 들어간다
- [ ] 커스텀 User로 바꾼 프로젝트에서도 가입·로그인·admin 로그인이 된다
- [ ] 옛 알고리즘의 해시로 로그인하면 새 알고리즘으로 다시 해싱된다
- [ ] 로그인하면 세션 ID가 바뀐다
- [ ] API 라우트를 토큰으로 호출할 수 있다

### M6. Admin

- 모델에서 생성된 목록·생성·수정·삭제, 페이지네이션, 목록 필터(생성된 Go가 조립) (D-48)
- 표시·숨김·필수·읽기 전용은 태그에서만, 이름으로 추측하지 않음 (D-49)
- 로그인한 사용자만 접근 (M5)
- 모델별 권한(M5)을 따른다
- admin의 CSS·JS는 admin이 미리 만들어 `embed.FS`로 싣는다(M7의 정적 파일 흐름이나 Tailwind에 기대지 않는다)

할일
- 커스터마이징(Django `ModelAdmin`, SQLAdmin의 `ModelView`처럼): 목록에 보일 컬럼, 검색할 필드, 필터, 정렬,
  폼 필드의 순서와 묶음, 일괄 동작, 모델마다 admin에서 뺄지. 필드를 가리키는 법은 D-48을 따른다: 문자열 필드 이름
  (`list_display = ["title"]` 같은 것)이 아니라 태그나 생성된 타입 있는 코드로. D-49("표시·숨김·필수·읽기 전용은
  태그에서만")와 어디서 나누는지 정한다
- admin 화면의 모양 바꾸기(템플릿 오버라이드, D-42는 v1)와 admin에 사용자 화면 더하기는 v1 목록

완료 조건
- [ ] 필드 이름이 `password`여도 태그가 없으면 숨겨지지 않는다(추측 금지 확인)
- [ ] 로그인하지 않으면 admin에 들어갈 수 없다
- [ ] 권한이 없는 모델은 목록에 보이지 않고 URL로 들어가도 403이다
- [ ] 목록 컬럼 지정 같은 커스터마이징 하나가 골든으로 검증된다

### M7. 정적 파일과 업로드

D-69(5분 흐름)에는 필요 없지만 v0에 넣는다. M4가 커지지 않게 따로 뒀고, 업로드의 접근 권한이 M5의 사용자를 쓰므로 M5 뒤다.

할일
- 정적 파일: 위치, 개발·배포에서의 서빙, 내용 해시를 붙인 이름과 압축으로 캐시 버스팅, 템플릿에서 해시 이름을
  얻는 함수(없는 파일은 생성 오류). 정할 것: 해시·압축을 `gen`에서 할지 서빙 때 할지(D-65 속도, D-67 생성물 커밋),
  압축은 gzip(stdlib)만인지 brotli(외부 의존, 루트 모듈에는 둘 수 없다: D-09·D-90)까지인지
- Tailwind CSS: 사용자가 Node·npm 없이 쓸 수 있게 프레임워크가 붙여 준다. 템플릿에서 쓴 클래스로 CSS를 만들어 정적
  파일 흐름에 태운다. 정할 것: 공식 standalone 실행 파일을 받아 돌릴지(네트워크·플랫폼별 파일, 새 종류의 외부 의존),
  다른 길이 있는지. 템플릿의 동적 클래스와 빌드에서 빠지는 클래스를 어떻게 다룰지
- 파일 업로드와 미디어: 폼의 파일 필드(M4 폼에 더한다), multipart 해석, 크기 제한(넘으면 413), 저장 위치(미디어 폴더,
  나중에 외부 저장소), 파일 이름 정리와 경로 벗어나기(path traversal) 막기, 내용 형식 확인, 실패 때 정리, 올린 파일의
  서빙과 접근 권한(M5의 사용자). D-72의 "이미지 처리는 범위 밖"과의 경계

완료 조건
- [ ] 템플릿의 `{{static "없는.css"}}`가 생성 오류이고, 있는 파일은 해시가 붙은 이름으로 나온다
- [ ] 파일 내용이 바뀌면 이름이 바뀌고, 해시 이름의 응답은 오래 캐시되는 헤더를 가진다
- [ ] Node 없는 환경에서 템플릿에 Tailwind 클래스를 쓰면 그 클래스가 든 CSS가 나온다
- [ ] 크기 제한을 넘는 업로드는 413, `../`가 든 파일 이름은 미디어 폴더 밖에 쓰이지 않는다
- [ ] 권한이 없는 사용자는 비공개 미디어를 받을 수 없다
