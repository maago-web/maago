# 철학

Maago의 결정은 아래 원칙에서 나온다. 결정이 원칙과 부딪히면 결정을 고친다.
괄호 속 번호는 그 원칙이 낳은 결정이다([DECISIONS.md](DECISIONS.md)).

## 1. 에이전트가 쓰고, 기계가 검증한다

에이전트는 기억이 없고, 그럴듯하게 틀리고, 오류 메시지를 그대로 믿고 고친다. 그래서 틀림은
사람의 리뷰나 운영 환경이 아니라 **생성 시점에** 잡혀야 하고, 오류는 위치와 고치는 법을 함께
말해야 한다. 태그도 SQL도 템플릿도, 컴파일러가 못 보는 문자열은 전부 생성기가 컴파일러 역할을
대신한다. 런타임 reflect가 0인 것도 같은 이유다. 검사는 실행 전에 끝나 있어야 한다.
(D-17, D-22, D-42, D-59~D-66)

## 2. 쓰기는 공짜, 읽기는 사람 몫

에이전트가 쓰면 장황함의 비용은 거의 0이다. 쿼리를 쓰임새별로 나누고, 결과 타입을 따로
선언하는 것은 싸다. 그러나 **리뷰하는 것은 사람이다.** 그래서 문법은 한눈에 읽혀야 한다.
에이전트가 쓰는데도 SQL 문법의 모양을 여러 번 다시 고른 이유가 이것이다.
**단, 장황함은 검사될 때만 싸다.** 반복된 사실마다 기계가 대조할 원천이 하나 있어야 한다. 대조하지 않는 복사는
버그 농장이다: 게시판의 "초안은 작성자만"은 SQL 셋과 Go 하나에 손으로 복사되어 31단계 동안 한 곳이 비어 있었고,
문서도 시험이 읽는 것만 낡지 않았다(M9 연구).
(D-13, D-23, D-152, SQL 규칙 3)

## 3. 규칙은 손에 꼽게

에이전트는 예외 목록에서 가장 많이 틀린다. 규칙이 늘어날 것 같으면 기능을 줄인다.
SQL 규칙은 여섯 개이고 더 늘리지 않는다. 여섯째(읽기 정책)는 새 검사라 늘었다: 있는 규칙의 해석은 세지 않고,
새로 생긴 검사는 센다. 조건 문법이 복잡해지면 문법을 키우지 않고
Go에서 bool로 계산해 넘기게 한다.
(D-24, SQL 규칙 3)

## 4. 한 기호는 한 뜻

같은 기호가 자리에 따라 다른 뜻이면, 규칙이 문서 뒤로 숨는다. `:x?`처럼 위치마다 동작이
달라지는 문법은 깔끔해 보여도 버렸고, `|`가 OR로 쓰이자 다른 자리에서는 뺐다.
(태그와 SQL의 기호 표)

## 5. 보이는 대로 동작한다

주석은 동작을 바꾸지 않는다. 숨은 쿼리도, 숨은 분기도 없다. 관계는 ID로 들고 JOIN은 SQL에
보이게 쓴다. 라우트는 한 표에 모이고, 조건부 SQL은 `{ }` 안에 드러난다.
(D-12, D-14, D-22, D-40, 줄 뒤 주석 조건·주석 라우트 기각)

## 6. 추측하지 않고 거부한다

허용되는 것은 닫힌 목록이다. 모르는 태그 키, 섞인 조건, 애매한 이름 변경을 만나면 추측하지 않고
"did you mean"과 함께 실패한다. 필드 이름으로 숨길지 말지를 짐작하지도 않는다.
(D-17, D-36, D-49, SQL 규칙 3)

## 7. 조용히 버리지 않는다

값이 없는 것과 해석에 실패한 것은 다르다. 지원하지 않는 필드는 사라지지 않고 이유를 남긴다.
일부만 채운 모델은 존재하지 않는다. 경고는 없고 오류만 있다. 통과했는데 사실은 검사가
빠졌던 경우도 없다. 의도된 예외는 파일 안에 적는다.
(D-18, D-23, D-37, D-43, D-63, D-64)
